# Obsidian checks and recordings in Docker

Use this environment for future Obsidian verification and demo recordings. It runs the actual Linux Obsidian application inside a container, with Xvfb providing a virtual display and FFmpeg recording that display. It does not open the user's desktop Obsidian application.

The container creates a disposable vault containing synthetic diagrams and the built plugin. Personal notes, the user's Obsidian configuration, and account credentials must not be mounted into the container.

## Run the checks

Install and start a Docker engine, then run these commands from the repository root:

```sh
npm run docker:check
```

This command prepares the container and runs the Obsidian checks against the synthetic vault. The first run needs network access to download the base image, dependencies, and Linux Obsidian distribution. Later runs can reuse Docker's build cache.

The checks detect which renderer Obsidian uses. Up to 1.14 it is Mermaid.js, and the checks also measure the plugin's connector docking. From 1.15 it is Pele, and the checks confirm that its connectors are orthogonal. With either renderer they check the plugin's palette and highlight colors in both themes. They hover nodes and a connector, then check that the ancestor path is traced, other elements fade, and the trace clears. They repeat the hover in a popout window and check that an opted-out diagram stays untouched.

### Obsidian updates and early-access builds

Obsidian delivers app updates as `obsidian-x.y.z.asar` files, which its installer loads from the profile. To check a version that has no Linux installer yet, such as an early-access build, pass its update file:

```sh
mkdir -p artifacts/obsidian-update
cp "$HOME/Library/Application Support/obsidian/obsidian-1.15.0.asar" artifacts/obsidian-update/
OBSIDIAN_ASAR=artifacts/obsidian-update/obsidian-1.15.0.asar npm run docker:check
```

Copy only the update file, never the application data folder. `artifacts/` is ignored by Git and excluded from the image. The file is mounted read-only and copied into the container's disposable profile. The container still has no network access. Results go to `artifacts/docker/obsidian-1.15.0/`, and `report.json` records the running app version (`obsidian`), the `installer`, the `update` file, and the `renderer`.

## Record the demonstration

```sh
npm run docker:record
```

The recording uses the container's virtual display and the everyday grocery-delivery scenario in `demo-vault/Examples/grocery-delivery.md`. It tours one complex flowchart in both themes without scrolling. Results are exported under `artifacts/docker/`:

| Artifact | Purpose |
| --- | --- |
| `obsidian-light.png` | Actual Obsidian in the light theme |
| `obsidian-dark.png` | Actual Obsidian in the dark theme |
| `obsidian-light-trace.png`, `obsidian-dark-trace.png` | A traced path while a node is hovered, generated by `docker:check` |
| `obsidian-popout-trace.png` | A traced path in a popout window, generated by `docker:check` |
| `report.json` | Application/plugin versions, theme samples, node count, and captured application errors |
| `obsidian-demo.mp4` | Demonstration at 30 frames per second, generated by `docker:record` |
| `obsidian-demo.gif` | GIF at 12 frames per second, generated by `docker:record` |
| `failure.png` | Application screenshot when a check fails after startup |

Inspect these artifacts before replacing the published README media. Never label Chromium-only recordings as Obsidian recordings. Failed runs may leave previous artifacts in this directory; check the command's exit status and file timestamps.

The existing unit and browser suites, linters, and strict TypeScript checks remain available through `npm run check`. Docker installs `tsx` and runs the TypeScript tools inside the container. They complement the application checks: the browser suite can exercise many graph shapes quickly, while the Docker workflow checks plugin behavior in Obsidian itself.

## Isolation and reproducibility

- Keep the vault synthetic and disposable. Do not mount the user's vault or Downloads demo vault.
- Keep app state inside the container. Only generated artifacts should be exported to the host.
- The runtime container uses `--network=none`. Its only bind mount is the artifact output directory; source and dependencies are copied into the image during the build.
- Record the Obsidian and plugin versions with the results, so published media can be traced to the tested build.
- On macOS, Docker runs Linux through a virtual machine. Linux application results do not establish compatibility with every macOS, Windows, or mobile installation.

## Verification status

Verified on 2026-10-09 with Linux ARM64 Obsidian 1.14.4 and plugin 0.1.2 inside Docker/Colima. `docker:record` passed 20 unit tests, 14 browser integration tests, the build, and real-app checks for both themes, ancestor highlighting, and 18 centered connector endpoints. A 15.2-second MP4 (1440 × 1000, 30 fps) and GIF were generated; representative frames were visually checked. See the [capture report](assets/obsidian-capture-report.md).

Verified on 2026-10-23 with Linux ARM64 Obsidian 1.14.4 and with the 1.15.0 early-access update file loaded on the same installer. Both `docker:check` runs passed the full `npm run check` (46 unit tests, 19 browser integration tests) and the real-app checks in both themes. On 1.14.4 (Mermaid.js), all 18 connector endpoints were centered. On 1.15.0 (Pele), every connector was orthogonal. Both versions showed the plugin's palette and highlight colors. Hovered nodes and a connector traced their paths and faded other elements, and the path cleared after the pointer left. Tracing also worked in a popout window, and the opted-out diagram stayed untouched. With the first plugin build, the same 1.15.0 check failed: hovering a node left its ancestors untraced. `docker:record` also completed the grocery tour on both versions.

The legacy `npx tsx scripts/record-obsidian-demo.mts` entry point also routes to Docker and never starts the host Obsidian app.

The grocery recording has 17 nodes and 22 flowchart connections. The endpoint-center metric is diagnostic for this mixed-shape diagram; it is not a strict centered-docking guarantee for every Mermaid shape. The smaller `docker:check` fixture retains its strict centered-endpoint assertions.

Recorder callbacks execute inside the browser. The Docker entrypoint runs `test-obsidian-docker.mts` through Node’s native `--experimental-strip-types`, preserving callbacks without transpiler helper functions. Use the same flag for `scripts/record-demo.mts`; other developer tools and unit tests run through `tsx`.
